# RISC-V Core Microarchitecture Specification v0.1

## 1. Purpose

This document defines the initial microarchitecture of the RISC-V processor core used in the RISC-V Heterogeneous SoC project.

The objective is to establish an implementable and verifiable processor microarchitecture before RTL development.

The initial implementation targets a 64-bit in-order RISC-V core compatible with the RV64GC architectural target defined in the system specification.

---

## 2. Microarchitecture Overview

The processor uses a classic five-stage in-order pipeline:

```text
IF → ID → EX → MEM → WB
```

Where:

* **IF** — Instruction Fetch
* **ID** — Instruction Decode and Register Read
* **EX** — Execute, Branch Resolution and Address Generation
* **MEM** — Data Memory Access
* **WB** — Register Writeback

The design prioritizes:

1. architectural correctness;
2. deterministic behavior;
3. verification simplicity;
4. modularity;
5. progressive performance optimization.

---

## 3. Processor State

### 3.1 Program Counter

The processor maintains a 64-bit program counter:

```text
PC[63:0]
```

The PC normally advances according to the instruction length and control-flow instructions.

The initial implementation must support the instruction encodings required by RV64GC, including compressed instructions.

### 3.2 Integer Register File

The core contains:

```text
32 × 64-bit integer registers
```

Register `x0` is hardwired to zero.

Reads of `x0` always return zero.

Writes targeting `x0` are ignored.

The register file provides two read ports and one write port.

---

## 4. Pipeline Stages

### 4.1 Instruction Fetch — IF

Responsibilities:

* generate the instruction address;
* request an instruction from the instruction-memory interface;
* receive the instruction;
* calculate the sequential PC;
* handle redirects generated by branches, jumps, exceptions or traps.

Initial interface:

```text
if_req
if_addr
if_valid
if_ready
if_rdata
```

The interface will later be connected to the instruction cache.

---

### 4.2 Instruction Decode — ID

Responsibilities:

* decode the instruction;
* identify the instruction class;
* extract register indexes;
* generate immediates;
* read the register file;
* identify required execution resources;
* generate control signals.

The decoder must distinguish at minimum:

* integer ALU operations;
* immediate operations;
* loads;
* stores;
* conditional branches;
* jumps;
* upper-immediate instructions;
* system/CSR instructions.

Compressed instructions must be expanded or normalized into an internal representation before execution.

---

### 4.3 Execute — EX

Responsibilities:

* integer ALU operations;
* comparison operations;
* branch condition evaluation;
* branch target calculation;
* jump target calculation;
* load/store address generation;
* CSR-related execution where applicable.

The initial ALU supports 64-bit integer operations required by the selected ISA subset.

Branch instructions are resolved in EX.

---

### 4.4 Memory — MEM

Responsibilities:

* issue load requests;
* issue store requests;
* interface with the data-cache subsystem;
* process returned load data;
* handle memory-operation stalls.

The processor does not directly implement a physical DRAM controller.

The memory hierarchy is abstracted behind a memory interface and will later be connected to the L1 data cache.

Initial interface:

```text
mem_valid
mem_ready
mem_addr
mem_wdata
mem_wstrb
mem_we
mem_rdata
```

---

### 4.5 Writeback — WB

Responsibilities:

* select the value written to the register file;
* write results from ALU operations;
* write load results;
* write appropriate CSR/system results where applicable.

The writeback stage must ensure that writes to `x0` have no architectural effect.

---

## 5. Pipeline Registers

The initial pipeline contains four explicit pipeline-register boundaries:

```text
IF/ID
ID/EX
EX/MEM
MEM/WB
```

### 5.1 IF/ID

Contains information required by the decode stage:

```text
pc
instruction
valid
```

Additional metadata may be added when required by compressed instructions, exceptions or instruction-fetch faults.

### 5.2 ID/EX

Contains:

```text
pc
decoded instruction information
rs1_value
rs2_value
rs1_index
rs2_index
rd_index
immediate
control signals
valid
```

### 5.3 EX/MEM

Contains:

```text
alu_result
store_data
rd_index
memory control signals
writeback control signals
branch information
valid
```

### 5.4 MEM/WB

Contains:

```text
memory_data
alu_result
rd_index
writeback selection
writeback enable
valid
```

The exact signal-level definition will be refined before RTL implementation.

## 6. Datapath

The initial datapath follows:

```text
                    ┌──────────────┐
                    │ Instruction │
                    │    Fetch    │
                    └──────┬───────┘
                           │
                         IF/ID
                           │
                    ┌──────▼───────┐
                    │    Decode    │
                    │ + Reg. File  │
                    └──────┬───────┘
                           │
                         ID/EX
                           │
                    ┌──────▼───────┐
                    │     ALU      │
                    │ Branch Unit  │
                    │ Addr. Gen.   │
                    └──────┬───────┘
                           │
                        EX/MEM
                           │
                    ┌──────▼───────┐
                    │    Memory    │
                    │    Access    │
                    └──────┬───────┘
                           │
                        MEM/WB
                           │
                    ┌──────▼───────┐
                    │  Writeback   │
                    │  Mux + Reg.  │
                    │     File     │
                    └──────────────┘
```

## 7. Data Hazards

The core must detect read-after-write dependencies between instructions in the pipeline.

The initial implementation supports:

* EX/MEM forwarding;
* MEM/WB forwarding;
* load-use hazard detection;
* pipeline stalls when forwarding cannot resolve a dependency.

Example:

```text
ADD  x5, x1, x2
SUB  x6, x5, x3
```

The `SUB` instruction must receive the newly produced value of `x5` through forwarding rather than waiting for architectural register-file writeback.

---

## 8. Load-Use Hazard

A load result is not immediately available for the instruction directly following the load.

Example:

```text
LD   x5, 0(x1)
ADD  x6, x5, x2
```

The hazard unit must detect this condition.

The initial policy is:

```text
detect dependency
      ↓
stall pipeline
      ↓
allow load result to become available
      ↓
resume dependent instruction
```

The exact stall timing will be validated by RTL simulation.

---

## 9. Control Hazards

Branches and jumps create control hazards.

The initial implementation resolves conditional branches in the EX stage.

When a control-flow instruction changes the next PC:

```text
wrong-path instructions
        ↓
      flush
        ↓
redirect PC
```

The initial branch strategy does not require a dynamic branch predictor.

A simple static/sequential fetch policy will be used initially.

Branch prediction may be introduced later as a measured optimization if performance results justify it.

---

## 10. Pipeline Control

The pipeline requires centralized control for:

* stalls;
* flushes;
* pipeline-register enables;
* PC redirection;
* exception/trap redirection;
* reset behavior.

Priority between control events must be explicitly defined.

The initial priority is:

```text
Reset
  ↓
Trap / Exception / Interrupt
  ↓
Control-flow redirect
  ↓
Pipeline stall
  ↓
Normal execution
```

This ordering will be validated during implementation.

---

## 11. CSR and Privileged Architecture

The processor targets the M/S/U privilege model.

The CSR subsystem will eventually provide the architectural state required for:

* machine-mode firmware;
* supervisor-mode software;
* trap handling;
* interrupt handling;
* virtual memory;
* Linux SMP execution.

The first RTL milestone does not require the complete privileged architecture.

CSR support will be introduced incrementally and verified independently.

---

## 12. Exceptions and Interrupts

The processor must provide a mechanism for redirecting execution to a trap handler.

The architecture must eventually support:

* illegal instruction exceptions;
* instruction access faults;
* load/store access faults;
* breakpoint exceptions;
* environment calls;
* timer interrupts;
* external interrupts.

Trap handling will be implemented progressively.

---

## 13. Memory Interface

The core is intentionally decoupled from the cache and memory implementation.

The processor exposes separate instruction and data interfaces.

```text
Core
 ├── Instruction Interface
 │        ↓
 │      L1 I-Cache
 │        ↓
 │      Memory System
 │
 └── Data Interface
          ↓
        L1 D-Cache
          ↓
        Memory System
```

This separation allows the processor core to be verified independently from the cache hierarchy.

---

## 14. Reset Behavior

At reset:

* pipeline registers are invalidated;
* architectural state is placed in a defined reset state;
* the program counter is initialized to the implementation-defined reset vector;
* no instruction may commit before the pipeline is correctly initialized.

The exact reset vector will be defined by the SoC memory map.

## 15. Verification Strategy

The core will be verified progressively.

### Level 1 — Unit Verification

Individual components:

* ALU;
* register file;
* immediate generator;
* instruction decoder;
* branch unit;
* CSR unit;
* hazard unit;
* forwarding unit.

### Level 2 — Pipeline Verification

Verify:

* arithmetic instructions;
* dependencies;
* forwarding;
* stalls;
* branches;
* jumps;
* loads/stores;
* pipeline flushes.

### Level 3 — Architectural Verification

Compare execution against a trusted RISC-V reference model where appropriate.

Candidate references include:

* Spike;
* QEMU.

### Level 4 — System Verification

Integrate the core with:

* caches;
* coherent interconnect;
* memory;
* interrupt controller;
* DMA;
* accelerator.

## 16. Performance Metrics

The processor implementation will be evaluated using:

* clock frequency;
* CPI;
* IPC;
* instruction throughput;
* branch penalty;
* load-use penalty;
* cache miss impact;
* memory latency;

Performance optimizations must be justified using measurements rather than assumptions.

## 17. Implementation Principles

The implementation follows these principles:

1. **Correctness before performance.**
2. **Specification before RTL.**
3. **Unit verification before subsystem integration.**
4. **Measured optimization rather than premature optimization.**
5. **Modular interfaces between processor, cache and memory subsystems.**
6. **Every architectural change must be documented.**
7. **Simulation and FPGA behavior should remain reproducible.**

## Register File Specification

### Purpose

The register file stores the integer architectural registers used by the processor datapath.

### Architecture

- 32 architectural integer registers: x0 through x31.
- Register width: 64 bits.
- Two combinational read ports.
- One synchronous write port.
- Read addresses and write address are 5 bits wide.
- Write data and read data are 64 bits wide.

### Behavioral Rules

- Reads of x0 always return zero.
- Writes to x0 are ignored.
- A write occurs on the rising edge of clk when we is asserted and rd is not zero.
- Reads are combinational.
- Registers x1 through x31 are not reset by this module.
- The contents of x1 through x31 are unspecified until software or hardware writes valid values to them.

### Verification Requirements

- Verify that reads from x0 always return zero.
- Verify writes to ordinary registers.
- Verify that writes to x0 are ignored.
- Verify simultaneous reads from two different registers.
- Verify read-after-write behavior.
- Verify that writes are disabled when we is low.
- Verify behavior immediately before and after the rising clock edge.
- Verify reads and writes using boundary values, including zero, the most significant bit, and all bits set to one.



## Instruction Decoder Specification — Version 0.1

### Purpose

The instruction decoder identifies supported RV64I integer register-register instructions and generates the control signals required by the datapath.

### Supported Instructions

The initial decoder supports the following R-type instructions:

- ADD
- SUB
- SLL
- SLT
- SLTU
- XOR
- SRL
- SRA
- OR
- AND

All supported instructions use opcode `0110011`.

### Inputs

- `instr`: 32-bit instruction word.

### Outputs

- `rs1`: 5-bit source register address.
- `rs2`: 5-bit second source register address.
- `rd`: 5-bit destination register address.
- `alu_op`: ALU operation selector using `core_pkg::alu_op_t`.
- `reg_write`: register-file write enable.
- `illegal_instr`: asserted when the instruction is not supported.

### Behavioral Rules

- Supported instructions are identified using opcode, funct3, and funct7.
- For supported instructions, `reg_write` is asserted and `illegal_instr` is deasserted.
- For unsupported encodings, `reg_write` is deasserted and `illegal_instr` is asserted.
- For unsupported encodings, `alu_op` defaults to `core_pkg::ALU_ADD`; this default must not be interpreted as a valid operation when `illegal_instr` is asserted.
- The decoder does not execute instructions or access the register file directly.
- Immediate instructions, loads, stores, branches, jumps, CSR instructions, and compressed instructions are outside this initial scope.

### Verification Requirements

- Verify each of the ten supported instructions.
- Verify extraction of `rd`, `rs1`, and `rs2`.
- Verify that unsupported opcodes are marked illegal.
- Verify that invalid funct3/funct7 combinations are marked illegal.
- Verify that illegal instructions never assert `reg_write`.
